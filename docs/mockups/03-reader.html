CHAPTER 03 · 异步数据库与事务

事务与回滚：async with 到底包住了什么？

12 分钟 2 个知识点 来自 tiangolo/fastapi fastapi/dependencies/utils.py
先看结论
Session 负责“一次会话内的工作单元”，事务负责“要么全成功、要么全失败”。async with 退出时，没有异常就 commit，有异常就 rollback，最后把连接还给池子——三件事的顺序不能换。

把 Depends(get_db) 展开看，一个请求的生命周期其实是四个动作：取连接 → 开事务 → 执行 → 提交或回滚。很多“数据莫名没写进去”的问题，都是这四个动作里有一环被提前打断了。

一个请求里的四步

app/db.py Python · 18 行 
1async def get_db() -> AsyncIterator[AsyncSession]:
2    async with SessionLocal() as session: # 取连接 + 开事务
3        try:
4            yield session               # 交给路由
5            await session.commit()      # 没异常才提交
6        except Exception:
7            await session.rollback()
8            raise
9
10@app.post("/tasks")
11async def create_task(body: TaskIn, db=Depends(get_db)):
12    db.add(Task(**body.model_dump()))
13    await db.flush()                # 拿 id，不提交
14    return {"id": task.id}

注意第 13 行的 flush 和第 5 行的 commit 不是一回事：flush 只是把 SQL 发给数据库、拿到主键，事务仍然开着；真正落盘要等依赖退出时 commit。这也解释了为什么在路由里再写一次 await db.commit() 容易出问题——提交了第一次，后面的 rollback 就救不回来。

常见坑

1. 路由里手动 commit 之后抛异常，依赖层的 rollback 已经无事可做，前半段写入变成“部分成功”。

2. 在 yield 之后再取 request.state 这类请求级对象，可能已经被回收；清理逻辑要放在 yield 前拿好引用。

回到仓库
